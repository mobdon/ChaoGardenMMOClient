# Chao Garden client implementation requirements

The user requires Rust for game systems, shared mechanics and game-format readers/converters. Browser execution of shared mechanics should use the agreed Rust/WASM boundary. Implement authoritative progression, care, training, rewards, inventory, identity and saves in the separate Rust server/core; browser or Android adapters render state and submit bounded intents.

The generated Vibe Expo mobile app, NestJS server and TypeScript simulation are unaccepted. They are not a completed Rust port or a replacement for the working Rust authority. Their source existing in Git does not establish acceptance. Preserve the current browser rendering/asset presentation while replacing no game system with an alternative TypeScript authority.

Read `TASKS.md`, `docs/DESIGN.md` and the server repository's `docs/coordination/BOARD.md`, `PROTOCOL.md`, `VIBE-REVIEW-2026-11-18.md` and `VIBE-PR7-REVIEW-2026-11-18.md` before new integration work. Repository identities are `mobdon/ChaoGardenMMOClient` and `mobdon/ChaoGardenMMOServer`. This combined checkout keeps the server independently under ignored `server/`; keep their Git histories/source boundaries separate.

- Client/Android presentation belongs in this repository; server production authority belongs in the server repository. Platform glue must consume real, agreed Rust contracts. Do not invent REST/auth/snapshot APIs and label them connected.
- Mobile is strictly Tiny Garden: same Chao, care/stats, AFK training and five minigames. Android widget is viewing/quick care with full activities opening Tiny Garden. A browser mockup is not an installed widget, and a tested Rust job ledger is not durable service integration.
- Preserve the canonical Chao, credentials/owner state, rings, stats, gear, resident opt-in and Tiny receipts. Trusted time/rewards and once-only results are server decisions; cached/offline UI cannot upload claimed gains.
- Preserve native Chao rigs/proportions and use Chao motions first. Keep installed games, ROMs, converted native assets, saves and credentials local/ignored. Reader/converter tooling does not prove a full game-engine port.
- Always use native game effects and assets first. Search the installed sources and inventory before any fallback. Never substitute a handmade effect or repurpose another effect when the matching original exists. Preserve original geometry, textures or vertex colors, material/alpha behavior and proportions; identify any attachment or timing adaptation explicitly.
- Use isolated branches/worktrees and coordinate shared entry points/protocol changes through the server board. Preserve other chats' work and the live preview/save. Source review/publication does not authorize runtime rollout or migration.
- Run checks appropriate to changed Rust cores and browser/platform adapters; prove an actual canonical service round trip. Record exact source, evidence and remaining limitations. Generated code/checklists and mock-only tests are not acceptance.
